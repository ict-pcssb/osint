## 首页到时间轴

1. **先确定游客已经给了什么。** 从注册资料、首页表单、本次对话和当前地图选点读取信息。注册意向城市只作为目的地线索。单问“周六开放吗”直接核实；申请规划整程时，才补问会改变安排的信息。
2. **固定安排优先。** 把游客口述或首页提供的抵达、返程、必去点和预订时段作为约束。沿用本项目明确的范围，无需票面上传、识别和票面字段。
3. **按缺口调用。** 要比较跨城方式时用 S3，查住宿用 E3，市内路段用 S8/E2，活动和餐馆候选用 S7，核查依据用 S6。天气 S5、费用 S4 使用行程日期和同行人数。
4. **返回当天的站点。** 已确认开放的地点排进正式行程，存疑的高成本去处进备选。涉及多花钱、多坐车、少半天游览或替换必去点时，让游客选。点开站点可见原因、来源和核查时间。打开旧行程复查走 E7，地图保留整条路线入口。

**建议的新站点格式**如下，为待开发的前后端契约。下面是结构示例，其中金额、时间及来源为空，空值在卡片上显示“待查”。同一站的开放、路况、费用可以各有自己的证据。

```json
{
  "date": "2026-11-28",
  "next_stop_id": null,
  "stops": [{
    "id": "qingyan",
    "name": "青岩古镇",
    "plan_role": "alternative",
    "opening": {"status": "unconfirmed", "applies_to": "2026-11-28"},
    "arrival_local": null,
    "leg": {"from": "贵阳北站", "mode": "taxi", "duration_min": null},
    "cost": {"unit": "vehicle", "currency": "CNY", "low_fen": null, "high_fen": null},
    "evidence_ids": [],
    "requires_user_choice": true
  }]
}
```

示例中青岩仍是备选。已有正式站时，让 `next_stop_id` 指向正式行程中可前往的站；尚无正式站时返回 `null`。证据记录至少包含来源名或 URL、核查时间、内容适用日期、证据类型（公告、地图、独立到店体验、推广等）；快照和模拟资料标出 `data_mode`。短期记忆服务于本次对话。长期偏好按账号隔离，沿用用户选择的记忆开关，需求默认开启。公共文旅知识库与私有偏好分别读取。

## 网页搜索的 Skill 接线（2026-11-26）

新单智能体应把网页搜索统一绑定到 `travel-search.search_travel_sources`。必传 `query`（检索词）和 `subject`（地点／门店／线路）；用 `required_terms`、`source_domains`、`target_date` 描述合适来源的条件。服务优先查 Exa，有候选就返回，没有合适候选或服务异常时才查 AnySearch。已有公开链接需要核对原文时仍走原文读取能力；网页搜索本身返回标题、URL 和摘要。[完整参数、调用示例与返回格式](MCP接口调用手册.md)

| Skill | 何时调用、怎么用返回值 |
|---|---|
| S6 攻略核验、E5 开放／演出／末班车 | 对游客点名的具体说法检索，活动日期明确时传 `target_date`，时刻表另核方向、站点、适用班期。取 `sources[].url/excerpt` 回看原公告，按站点保存核查时间。无匹配就出待确认卡。 |
| S7 周末发现、E4 餐馆推荐 | 周边地点由地图提供；需活动公告或独立到店描述时检索。按作者、实际到访日、时段、是否推广核对。已否决的广告或旧攻略可用 `rejected_urls` 排除后再查。 |
| E6 景区费用、S4 预算 | E6 找景区官方票价、观光车公示及儿童条件，按票种提取金额、适用期和计价单位；S4 消费核实后的明细做算术。景区官网证据不足时保留缺价。例：`{"query":"梵净山 儿童门票 观光车 优惠","subject":"梵净山","required_terms":["观光车"],"source_domains":["fanjingshan.gz.cn"]}`。当前没有专门查景区实时报价或余票的 MCP。 |
| S5 天气改排、S9 路书补资料、E7 打开行程复查 | S5 的天气数值继续走天气 MCP，只有查景区停运等公告时用搜索；S9 有补来源需求才调用；E7 开发时按原站点逐项复查，将变化交给游客确认。 |
| S1/S2 主规划、S3 交通、E2 打车、E3 住宿 | 主规划消费以上已核实证据。高铁、航班、打车、酒店等结构化报价继续用各自的工具。 |

**处理结果。** `candidates` 先读原文，再生成事实或费用卡。`unconfirmed` 保留当前正式安排，标待查；`unavailable` 告知游客这一轮无法完成查询。`attempts` 可展示查过的供应商和核查时间。11 月 26 日的新工具实测覆盖 Exa 直接命中、Exa 无匹配后 AnySearch 命中，以及两家均无匹配。旧网站原有的 AnySearch 直连代码仍按旧路径执行；上表是新助手 Skill 的接入契约。

## 9 个已有 Skill 的接入契约

下表「当前返回」写实际入口可取的字段。部分旧 `SKILL.md` 给出了更理想的字段，下游应以实际入口为准。旧规划器内的 `rail.search`、`route.leg` 等是业务步骤名，注册外部工具时使用 MCP 手册里的工具名。

| Skill、何时用 | 入口、输入和依赖 | 当前返回 → 新项目处理 |
|---|---|---|
| **S1 贵州路线规划** `plan-guizhou-route`。给多日目的地排序、检查抵达和返程衔接。 | 原主执行器 `travel_plan.execute`，复用 `travel_planner_rules.arrange`。输入日期、起终点、同行人、出行方式、必去点、硬时段。读本地 POI 目录；路段可用 OSM `route`、高德 `maps_direction_driving`，跨城段由 S3 提供。 | 原 `trip_plan.days[].stops[]`、`legs[]`、`optional_stops`、`rule_checks`、`unresolved`、`evidence_ids`。**需改**。复用排日和冲突检查，为每站关联真实入口、上一段耗时、费用、来源、下一站。旧站至景区适配器要求已核对的车站与入口坐标；模糊地点先解析。 |
| **S2 行程规划草案** `travel-planner`。游客已给基本信息，先看天数、景点和大致预算。 | `POST /api/travel/skills/travel-planner`。传 `origin, poi_ids, start_date, end_date, travelers, budget_fen, budget_scope`；可传 `pace`。本地目录及预算规则，无需 MCP。 | `title, days[], poi_ids, budget.group_cap_fen, budget.missing_costs, pending[], sources[]`。**复用校验与草案**。旧入口限同一市州、主要景点数不多于天数。正式时间轴统一走 S1；跨市或一天多站不能直接套用该入口。 |
| **S3 跨城交通比较** `compare-intercity-transport`。查高铁或飞机，比较从出发地到实际目的地的时间和钱。 | 原铁路 `GET /api/travel/rail-day`，传站点目录 ID 和日期；12306 MCP 先 `get-station-code-by-names` 后 `get-tickets`。新项目主用 flights-mcp `search_flights`、可备用 fli；末段用 S8。 | 铁路 `trains[]`、车次、站点、时间、席别；航班 `flights[]`、航段、币种、价格；原主规划有 `railway, transport_options[]`。**需改**。旧航空函数和旧证据 URL 仍指向飞常准。接入新航班后统一人数、币种、接驳及查询时间，把需要比较的候选交给游客。 |
| **S4 行程预算** `check-trip-budget`。游客给全团或人均上限，或问“两人一共多少”。 | `travel_constraints.quote_lines`、`travel_plan.budget`。输入人数、房晚、计价单位、费用范围和有依据的价格；纯计算不调 MCP。价格按需来自 12306、航班、RollingGo、打车或有日期的官方票价资料。 | `lines[], known_lower_fen, upper_fen, budget_status, missing_costs[]`，金额单位为分。**可复用计算，需接入报价**。按人、房晚、整车分别乘数量；不确定上限为 `null`。新接入层同时承担多币种校验及儿童费用 E6。 |
| **S5 目的地天气及改排** `adapt-trip-weather`。游客单问天气，或户外站点可能受雨影响。 | `GET /api/travel/forecast-day?poi_id=qingyan&day=YYYY-MM-DD`；行程复用 `forecast(poi_id,start,end)`。Open-Meteo MCP `weather_forecast`，逐时空气质量可选 `air_quality`。运营变化另走 S6/E5。 | `location, kind, timezone, days[].hours, units, as_of`；原规划另有 `weather_alternatives[]`。**可复用直查；需补受影响站与可达备选**。县级预报标县区，超出窗口说明待查；原入口的未知地点也可能报 503，建议先解析地点。 |
| **S6 攻略来源核验** `verify-travel-sources`。游客发链接或指定一句话，或已有行程遇到信息冲突。 | 原 `travel_plan.retrieve` 调公共知识库 HTTP `/v1/retrieve`；`travel_weekend.research/confirmed_excerpt` 有原文和日期核查逻辑。新助手从统一搜索入口查找来源；已有链接可由 `/v1/extract` 读取，再核对官方公告。旧 Skill 中的 `notice.lookup` 须有真正的数据源，不能按名字假定已部署。 | 当前有 `hits[]`、证据 ID、摘录、`unresolved`，研究入口另有 `groups[].items[]`。**需改**。新入口按说法返回 `claim, status, evidence_ids, applicable_date, checked_at, recommendation`，列出冲突和备选。打不开请游客给截图或指出原话；广告仅作待查线索。 |
| **S7 周末吃喝玩乐** `weekend-city-trip`。按日期找餐馆、饮品、游玩地点和活动。 | `POST /api/travel/skills/weekend-city-trip`，传 `anchor_id, start_date, end_date, groups, radius_m`；可用 `/weekend-research` 按研究主题查资料。本地 OSM 快照、覆盖范围外的在线查询、按需 AnySearch 或公开公告。 | 分类接口返回 `groups[].places[], as_of, events`；研究接口返回 `groups[], route[], query_count, as_of`。**可复用发现，需接核验**。快照上的营业标签和候选地点保留采集时间，当晚营业、广告识别和独立评价由 E4/E5 处理。 |
| **S8 地图周边与路段** `osm-mcp`。游客在地图选点，查附近地点、步行或行程下一段。 | `POST /api/travel/skills/osm-tools`，传 `tool, arguments`；OSM MCP `route, find_nearby_pois, geocode, poi_details` 等。高德地点搜索、驾车路线可另选。输入明确起终点、坐标系、方式或类别半径。 | `result, source, source_url, as_of, data_mode`；路线读 `result.distance_m/duration_s`。**可复用**。保留地点候选、缓存原采集时间；无路和上游超时分别处理。OSM 为 WGS84 纬度在前，高德为 GCJ-02 经度在前。 |
| **S9 旅行路书** `travel-guidebook`。游客要从已有行程预览、下载或打印。 | `POST /api/travel/skills/guidebook/{preview,html,pdf}`，给标题、每日安排、来源及可选封面。排版无需 MCP；可选 `/supplement` 通过 AnySearch HTTP 补资料。导出用 Node、Playwright、Chromium 和可写临时目录。 | `preview` 返回包含 `html` 的 JSON；`html` 返回 HTML 文件，`pdf` 返回 PDF 字节。**可复用作导出**。默认视图仍是当天时间轴。导出失败保留 HTML 及浏览器打印入口。 |

## 7 项已讨论的扩展能力

下表返回字段是**建议给新助手的契约**。在当前项目找不到完整 Skill 的条目列出已测的组件，供开发时复用。

| 能力、触发 | 输入、依赖与调用顺序 | 建议返回；复用范围与缺口 |
|---|---|---|
| **E1 行程信息补全**。游客要规划整程或改变原安排。 | 先读注册、首页、当前地点/行程和已同意使用的偏好，再读当前消息。复用 `POST /api/travel/drafts/preview` 的 `task, overrides`；本步无需 MCP。 | `known_fields, missing_fields, next_question, choices, needs_confirmation`。已有 `trip, missing_fields`，部分场景有 `confirmations`。**需改**。注册模型有 `intended_region`，旧预览合并资料的 `Profile` 不含该字段。补映射、区分出发/意向/当前地；只问影响眼前决策的一项。 |
| **E2 打车估价**。游客单问“多少钱”，或行程需市内接驳。 | 起终点、城市、可选车型和时间。高德打车 MCP `get_taxi_service`：模糊起点返回候选，游客选定后带回当次上下文。需要普通出租车参考价时可另查高德驾车 REST `route.taxi_cost`。 | `pickup_choices[]` 或 `vehicle_quotes[], distance_m, duration_s, endpoints, checked_at, source`；区分整车参考价和车型区间。**新增 Skill，底层已通**。两次独立查询已验；同一会话“游客选点→回传→报价”的交互仍要验收。每次调用登记高德用量。 |
| **E3 住宿比较**。游客想省钱或愿意多花一些住得方便。 | 地点、入住日期、人数、房晚、次日第一站；RollingGo MCP `searchHotels → getHotelDetail`，必要时 S8 查真实路段。 | `hotels[], nightly_reference, stay_total, currency, cancellation, next_stop_leg, missing_costs`。**新增组合 Skill**，复用 `travel_hotels.py` 搜索和房型解析。实测房型有 `averagePrice`、币种和退改，大量条目缺 `totalPrice`。未取得供应商总价时标待确认；推算值须另标估算，不能承诺税费或退改。 |
| **E4 餐馆推荐与广告辨别**。游客问吃什么，或想比较攻略里的网红店。 | 位置、预算、就近/口味偏好、到店时间；S7/S8 找候选，S6 用可追溯原文或知识库取独立到店体验，必要时查营业。 | `primary, alternative, visit_time, verified_facts[], independent_reviews[], sponsored_claims[], uncertainties[]`。**新增判断流程**。位置、里程和吃喝候选可复用；实测点位中没有评价作者、实际到访日、广告标记。优先推荐近期独立到店证据更足的店；半年以前的口味体会保留原日期。 |
| **E5 开放、演出与末班车核查**。游客问“这个周六开不开”、要专程出发或要赶公交。 | 精确地点/线路/方向、实际到访日及时段；S6、统一网页搜索、知识库、主办方或场地方原公告、公交运营方时刻。尚无已验证的专用末班车 MCP。 | `claim, target_date, status, regular_hours, evidence[], checked_at, alternative`。**扩展 S6**。活动日期核查已有逻辑；现场反馈冲突、末班车方向和节假日例外需补。周六未确认就放在卡片首行；单程 40 分钟的夜市未确认恢复时，优先给已确认开放的夜间去处。 |
| **E6 景区费用明细**。游客问一家三口门票，存在儿童优惠和可选观光车。 | 日期、景区、成人数、儿童人数；条款有身高/年龄要求才追问，观光车是否选乘单列；S4 核算，S6/公共知识库查当日官方条款。本项目尚未接入专门查景区门票价格、库存的 MCP。 | `items[], eligibility, mandatory, unit, quantity, unit_fen, subtotal_fen, known_lower_fen, total_fen, pending_question`。**扩展 S4**。原 `quote_lines` 按同一 `travelers` 乘人数，旧逻辑不能直接算成人和儿童混合团。必需项缺价时总价保持空值。 |
| **E7 打开行程时自动复查**。游客重新打开保存的行程，某站有待确认或易过期事实。 | 行程 ID、站点 ID、原证据及核查时间、出游时间；按项目重新调用天气、报价或 E5 的资料源。已核实且仍有效的事实可复用缓存。 | `checked_at, station_changes[], previous, latest, source, suggested_switch, needs_user_choice`。**新增触发及状态保存**。原项目有工具缓存和来源时间；新项目尚无打开行程即逐站复查、保留原安排及确认替换的完整流程。失败只更新待查状态。 |

## 4 个待选场景

这些场景已有零件，可以等核心时间轴完成后再决定是否单独注册 Skill。尚无独立的完整实现可重复测试。

| 场景 | 何时用、调用什么 | 建议输出和边界 |

## 第一轮接入顺序

从 **E1 信息补全 → S1 路线 + S2 草案 → S8 逐段路线 → S4 费用 → 当天时间轴** 做一条可以让游客亲自走的行程。首个验收题可以沿用“贵阳两人两天、预算有限”：在首页时间轴上逐项对照下一站、怎么到、走多久、全团花多少、哪些仍待确认。随后接 S5 和 E2/E3，补齐天气、打车和住宿。涉及店铺评价、演出、开放和末班车时，接 S6/E4/E5，再用 E7 在打开行程时复查。
## Skill 与 Parallel 搜索的分工 · 2026-11-26

游客泛问“帮我搜一下”，新助手的默认工具约定是 `travel-search.search_travel_sources`（Exa 优先，AnySearch 备用）。指定用 Parallel 或值得补一份独立线索时，可显式调用 `parallel-search.web_search`；已有公开 URL 时可调用 `parallel-search.web_fetch`。不同搜索引擎返回同一篇文章，只算一个出处。

S6 攻略核验、E5 开放与交通、E6 景区费用可按上述方式查原文；E4 餐馆推荐还要核对到访日期和推广标记。Skill 负责判断要查什么和怎样采信，MCP 工具负责实际联网。项目已完成工具注册与本机调用；游客聊天入口到 Skill 的完整自动编排仍待接入。[参数及四题实测](MCP接口调用手册.md)
